# Angular compatibility of the collectors

Every Angular API the collectors read, the first version that ships it, and what changed up to Angular 22. The overlay checks each one on the page at runtime (`packages/devtools/src/ng-capabilities.ts`) and sends the result with the page's `pageId` (`report-page-angular`). The versions the panel and the agent tools name come from one table, `ANGULAR_FEATURE_NEEDS` in `packages/devtools/src/config.ts`.

## How this was checked

The `@angular/core` and `@angular/router` packages of these versions were packed with `npm pack` and their fesm bundles read, not run: 12.2.17, 13.4.0, 14.0.7, 14.3.0, 15.0.4, 15.2.10, 16.0.6, 16.1.9, 16.2.12, 17.0.9, 17.1.3, 17.2.4, 17.3.12, 18.0.7, 18.2.14, 19.0.7, 19.1.8, 19.2.25, 20.0.7, 20.1.8, 20.2.4, 20.3.33, 21.0.9, 21.1.6, 21.2.25, 22.0.8 and 22.2.2. "First version" is the first of these that has the API. The `window.ng` keys come from `publishDefaultGlobalUtils` (`globalUtilsFunctions`, and `externalCoreGlobalUtils` in 22), which development builds run at bootstrap. Production builds publish none of them.

## Router internals

`router.ts` reads the Router through `read()` guards, so a field an older router lacks is left out of the report. `navigationTransitions` (whose events the overlay prefers) exists from 15.0; before that the overlay subscribes to `router.events`. The overlay calls `currentNavigation` when it is a function and falls back to `getCurrentNavigation()`, which every version has. `withComponentInputBinding` exists from 16.0 and `routerOutletData` from 19.0.

| Field or behaviour                                             | First version                           | Before it                                                                                                                                                        |
| -------------------------------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type` (`EventType`) on router events                          | 14.0                                    | `routerEventType()` reads the class name from `toString()` (`NavigationStart(id: 1, url: '/')`), which every event has and minification keeps.                   |
| `Router.options` (the `forRoot` options)                       | 15.0                                    | Only the options the Router keeps as fields are read (`onSameUrlNavigation`, `paramsInheritanceStrategy`, `urlUpdateStrategy`), and none shows as set.           |

| `Router.pendingTasks.hasPendingTasksObservable`                | 20.0                                    | 16.0 to 19.x hold a `hasPendingTasks` subject, which `waitForStable()` reads; before 16.0 the Router has no pending tasks and the stability is unknown (`null`). |

## How it is tested

`.github/workflows/compat.yml` runs the page-side tests (`packages/devtools/vitest.compat.config.ts`) on Angular 12.2, 15.2, 17.3, 19.2, 20.0, 21 and 22, all on Node.js 22: the tests load Angular in jsdom with JIT, so they need no Angular CLI. Angular 12 ships View Engine bundles, so that job first compiles them for Ivy with ngcc from `@angular/compiler-cli` 12. The test helpers in `packages/devtools/src/__tests__/angular-version.ts` start TestBed, bootstrap an app (an NgModule before 14.1) and give zoneless change detection where each version has it.

`angular-real-app.test.ts` bootstraps a small app with a pipe, a directive and the router on each version and checks that `window.ng` has exactly the utils `ng-shapes.ts` lists for that version, that `detectAngular()` reports the capabilities in the first table, and that each collector gives data or its documented fallback. `private-api-canary.test.ts` checks each util and framework field by the versions above. A test of a feature the version lacks checks the unavailable result on that version instead of being skipped; tests are skipped only where the Angular API the test builds on doesn't exist, such as functional guards before 14.2 or `@defer` before 17.0. The real `@ngrx` tests run from 19.0, because the workspace installs `@ngrx` 22.

## Builds on older toolchains

These were checked by building an Angular 12.2 and an Angular 15.2 app with `@angular-devkit/build-angular:browser` (webpack) and `import('@pangular-inspector/devtools/overlay')` in `main.ts`; the Angular 12 build was also loaded in jsdom, where the overlay started and looked for the server.

- `signal-history.ts` imports `@angular/core/primitives/signals` with `/* webpackIgnore: true */`. webpack leaves the import to run time, where it fails and signal history falls back to samples (on 17 and 18 webpack builds too). Vite and esbuild resolve it; the Vite plugin aliases it to `signals-stub.ts` when the app's `@angular/core` is older than 17 (`vite-signals-stub.ts`).
- The dist files are `.mjs`, so webpack treats a named import of a missing export as an error. The overlay imports nothing by name that Angular 12 lacks; `untracked` is read at run time. `@pangular-inspector/devtools/http` imports `REQUEST` and `provideEnvironmentInitializer`, so it builds from Angular 19.0 only.
- `typesVersions` in `package.json` maps each entry to its `.d.mts` for `moduleResolution: node`, which Angular 12 to 16 apps use. TypeScript before 4.7 (Angular 12 and 13) can't read `.d.mts`, so those apps declare the module themselves (see the installation page).

## Not covered yet

- Angular 13, 14, 16 and 18 are in the peer range but not run in CI.
- The `application` (esbuild) builder of Angular 17 to 19 was not built against; it resolves the signal primitives like Vite.
- `@pangular-inspector/devtools/http` needs Angular 19.0. Reading `REQUEST` and `provideEnvironmentInitializer` without a named import would let it build from 15.0 (`withInterceptors`).
